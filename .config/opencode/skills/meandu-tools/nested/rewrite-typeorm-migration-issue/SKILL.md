# Rewrite TypeORM Migration Linear Issue

Rewrite a manage-api Phase 2 TypeORM-to-Prisma card (swap Store internals from TypeORM to Prisma) into a specification an autonomous agent executes correctly on the first pass.

> **Scope:** it operates on the manage repo at `/Users/paul/dev/manage` (read-only research) and writes to Linear. It **extends** the general skill at `/Users/paul/.claude/skills/meandu-tools/nested/linear-write/SKILL.md`; read that first for the base template, writing style, MCP tooling, and Linear save gotchas. This file only adds what migration cards need beyond it.

## Why this skill exists

These cards were burned by two failure classes, and the card structure below is the countermeasure to both:

1. **Plausible-but-wrong technical guesses in the original ticket.** CUSM-820's original card guessed `$queryRaw` was needed for array containment ('Pattern B likely'); verification showed `orderingType` is a Prisma scalar list, so `{ has }` compiles to the same `@>` operator. Every technical claim in the original must be verified against real code, and corrections recorded in a Q&A section, not silently fixed.
2. **Write-path incidents from bridging mappers.** Three production incidents (CUSM-770, CUSM-795, CUSM-796) came from outbound legacy-to-Prisma mappers silently dropping FK relations or skipping asymmetric scalar transforms. Read-path tests pass; writes silently mutate data on the next save. Every card must either apply the write-path audits or explicitly declare them N/A (see 'Write-path decision').

## Non-negotiables (repo invariants the card must encode)

- **Decouple return types**: replace `<Entity>Record = Omit<LegacyEntity, ...>` with a standalone local `Mapped<Entity>` interface. Zero `@mr-yum/legacy-entities` imports in the mapper file. Same field shape (names, scalar types, nullability) as what TypeORM returned, so snapshots hold. Land as its own type-only commit before the Prisma swap.
- **Mapper construction is strictest-first**: plain typed object literal, then explicit field assignment, then tighten/loosen the mapped type, conversion helper, or fail-loud `UnexpectedError`. Never `as`, never `Object.assign`. Existing Phase-1-era `Object.assign` mappers in the repo are the banned pattern; the card must warn the agent not to copy them, naming the specific file if one is adjacent.
- **Service-level integration spec** is the Phase 2 testing baseline (`test/integration/<domain>/<domain>.service.integration.spec.ts`), not store-level. Never mock the migrating layer: no `Repository`/`QueryBuilder` mock pre-swap, no store mock post-swap.
- **If a snapshot diffs, the query is wrong, not the snapshot.** No `jest -u` rubber-stamping (PR #3234 lesson). The card must say this verbatim in its 'When uncertain' block. One narrow exception (phase-2 § Porting when the legacy baseline itself has moved): the legacy side itself moved since the baseline was pinned, e.g. a typeorm version bump. Dead vs live is decided only by re-running the unmodified Phase 1 suite against current `node_modules`; a failure means the baseline is stale, and the fix is a re-pin FIRST, in its own commit, naming the changed typeorm behaviour and the `node_modules` file:line that proves it (model: `test/integration/cart/cart-store.integration.spec.ts`, 'drops a soft-deleted discount from the cart (0.3 join scoping)'). Never fold a re-pin into the swap commit.
- **Method names and parameter shapes are unchanged.** Only internals and return types move.
- **npm, not pnpm.** All verification commands in the card use `npm run ...`.
- Lift-and-shift semantics win over reviewer 'fixes', but the undefined-where rule is path-specific on `typeorm@0.3.30` (phase-2 divergence #3): a find-options `where` (`find`/`findOne`/`findBy`/`count`/`findAndCount`) DROPS an undefined key, same as Prisma, so no action; the QueryBuilder object-form `.where({...})`/`.andWhere({...})` and `update`/`delete` criteria paths still bind `= NULL` (matches nothing), so reproduce matches-nothing there. Grep the legacy call site for which shape it used; do not infer from the method name (`repository.update()` shares where-handling with `.where({...})`, not with `find()`). Never accept CodeRabbit `IsNull()`-style rewrites: `IsNull()` matches the null rows, a third behaviour neither side had.

## Workflow

1. **Fetch the issue** (`mcp__claude_ai_Linear__get_issue`). Identify the target store methods, the claimed Prisma equivalents, and every technical guess the original makes.
2. **Read the governing docs** (Step 0). Do not draft from memory of a previous card.
3. **Research and verify with subagents.** Fan out Explore subagents over `/Users/paul/dev/manage` rather than dumping files into the main thread. Verify, minimum:
   - each target method's actual TypeORM query, file, and line;
   - the Prisma model names in `schema.prisma` for each table (see footgun 1);
   - every consumer of each method (service delegators, resolver `@Parent()`/`@ResolveField`, dataLoaders) via callers plus `git grep`; real call-site evidence beats the ticket's claim;
   - every technical claim in the original card (Pattern A vs B, operator availability, nullability);
   - whether each target store's Phase 1 baseline predates the current typeorm pin (`git log` the spec vs the bump commit). If it does, the card must mandate re-running the unmodified Phase 1 suite first and, on failure, the re-pin flow from phase-2 § Porting when the legacy baseline itself has moved, before any swap work.
4. **Run the footgun sweep** (next section) against each target method. Every hit becomes a numbered 'Footgun N' block in Implementation guidance with the exact file:line evidence.
5. **Make the write-path decision** (section below) and encode it in Scope and Verification.
6. **Draft with the extended template** (base template plus the migration sections listed below). Study `references/exemplar-cusm-820.md` in this skill's directory for the target shape and density. If the work resolves to two or more separately mergeable PRs, apply the sub-issue split (next section) instead of one monolithic card.
7. **Cold-read test**: fork a subagent given ONLY the card text; ask for its implementation plan and every assumption it had to make. Fix each assumption in the card. On a sub-issue split, cold-read the sub-issue cards (they are the implementation contracts), not the parent.
8. **Present the draft, wait for approval, save** via `save_issue`, preserve the original description in a `+++ # Original description (pre-YYYY-MM-DD)` collapsible (Linear native syntax, never `<details>`), then **fetch the issue back** and confirm no bullets were clipped.

## Sub-issue split (parent overview + one card per PR)

**Criteria**: the rewrite lands on a stacked shape with two or more separately mergeable PRs, each a unit of work in its own right. The common trigger is a store unit of work with no existing baseline: PR 1 adds the service-level integration specs, PR 2 adds the store + swap. **Preference (Paul, 2026-07-09): split into sub-issues rather than one monolithic card.** Pattern source: CUSM-816 (children CUSM-833/834); instantiated by this skill on CUSM-285 (children CUSM-998/999). A single-PR rewrite (e.g. an internals swap on an existing store with Phase 1 baselines already merged, like CUSM-834 itself) stays one card; the split earns its ceremony only when the PRs merge separately.

- **One sub-issue per PR**, titled `[1/2] ...` / `[2/2] ...`, each a full agent-ready card via the extended template. The detail lives here: read matrix, seeding template, and spec-side traps on the tests card; footgun blocks, target-shape snippet, wiring, and verification greps on the swap card. Each carries its own Risk tier (tests-only is Low; the swap card carries the real tier and the Due diligence section).
- **The target issue becomes the parent overview**, a high-level TLDR that explains the full body of work and how the sub-issues fit together: Summary, Problem (method + consumers), Strategy (each sub-issue with a one-line scope, the merge order, and the zero-spec-edit contract binding them, including any sanctioned spec delta), Key findings and decisions from the rewrite, rollup ACs ('both sub-issues merged, in that order' plus cross-cutting invariants), overall Risk tier, the corrected-guess Q&A, and the original description collapsible with the precedence line rephrased 'The sub-issues win over the original description below'. No footgun detail on the parent.
- **Creation order**: sub-issue 1 first, then sub-issue 2 (which can cite sub 1's real ID; sub 1 refers forward generically as 'the sibling `[2/2]` sub-issue under <parent>'), then save the parent citing both. Sub-issues take the parent's team, project, milestone, assignee, and priority; set `parentId`. No blockedBy relations: stacked PRs can be worked in parallel, the parent's Strategy states the merge order.

## Footgun sweep (check every one, per method)

These are verified failure modes from real cards, not hypotheticals. For each target method, check:

1. **Prisma model-name transposition.** Model names in `schema.prisma` do not reliably match entity names; plural/singular can be transposed from intuition (in menuItemUpsell, `prisma.menuItemUpsellGroups` is the LINK table `menu_items_to_upsell_groups`, `prisma.menuItemUpsellGroup` is the GROUP). Confirm each model against `schema.prisma` and cite an existing already-migrated method that uses it correctly.
2. **Soft-delete is auto-scoped at the query ROOT AND at every joined relation on `typeorm@=0.3.30`, and Prisma auto-scopes nothing, ever.** (Derived from `typeorm@0.3.30`: `query-builder/SelectQueryBuilder.js:985-992` joins, `query-builder/QueryBuilder.js:544-557` root. This FLIPPED at the 0.2.30 to 0.3.30 bump, CKTF-1702, 2026-07-13.) `SelectQueryBuilder.join()` appends `<alias>.<deleteDateColumn> IS NULL` to any joined relation carrying `@DeleteDateColumn`, and `relations: [...]` loads through that same join path. So the Prisma port adds `deletedAt: null` at EVERY level, root and `include`d/nested relations, wherever the legacy read relied on auto-filtering. The CUSM-820 trap flipped direction with it: the reject condition is now UNDER-filtering (a joined relation missing `deletedAt: null` leaks soft-deleted rows), no longer over-filtering. Two carve-outs: `.withDeleted()` / `{ withDeleted: true }` disables scoping at BOTH levels via one flag, so a legacy read using it must NOT gain the filter (live pattern to cite: `marketing.service.ts` `venueMarketingOptIns` and `directPrinting.dao.ts:240`, which pair `.withDeleted()` with an explicit root-only `deletedAt IS NULL` andWhere, i.e. 'unscope the joins, keep the root scoped'); and a relation loaded as its own separate query is a root there, scoped on both versions, no change. The repo is deliberately MIXED post-bump (CKTF-1702 / #4217 restored some reads to 0.2 semantics, re-pinned others' baselines), so the rule keys off what the live call site does TODAY, not what typeorm does by default: read it, check for `.withDeleted()`, check whether its Phase 1 baseline was re-pinned post-bump. Verify the column exists first (some entities, e.g. `TableGroup`, have none); an unnecessary filter still silently drops valid rows. Governing text: the Phase 2 doc's soft-delete section (stamped) and divergence catalog.
3. **CockroachDB `{ not: true }` is not `IS NOT TRUE`.** The datasource is CockroachDB; `not: true` compiles to `<> $1`, which excludes `NULL`. For a nullable boolean, the faithful translation of `IS NOT TRUE` is `OR: [{ field: false }, { field: null }]`.
4. **Entity-level default ordering fires at the ROOT only (conclusion unchanged by the 0.3 bump; the trace moved).** `@Entity('table', { orderBy: { position: 'ASC' } })` gives TypeORM an implicit order ONLY when that entity is the root of the query (Derived from `typeorm@0.3.30`: `QueryExpressionMap.js:182-193` reduces over the main alias only; `relations: [...]` routes through `SelectQueryBuilder.buildRelations`, NOT `FindOptionsUtils.applyRelationsRecursively`, which 0.3 wires only into TreeRepository, so don't cite that plausible-sounding name). So distinguish the load path: when the ordered entity is the query root, Prisma has no default and you must reproduce the `orderBy` or the snapshot churns; when it is loaded as a relation via `relations: [...]` / `leftJoinAndSelect`, legacy returned those rows UNORDERED, so do NOT pin their order in Prisma or the snapshot (over-specifying beyond legacy is the same over-filter-class trap). The real ordering contract usually lives on the root-load path (typically the `@ResolveField` dataLoader loading the child as a root via `RelationLoader`); reproduce it there. Check the entity decorator AND how each consumer loads it, not just the query builder. One lever flips this: `relationLoadStrategy: 'query'` loads a relation as its own root query, where the default `orderBy` WOULD apply; the repo does not set it, so re-derive only if that ever changes. Governing text: Phase 1 doc's "Relation ordering" section (ref CUSM-954 / #4103) and Phase 2 divergence catalog #4.
5. **DataLoader / `@Parent()` seams.** Resolvers binding `@Parent() x: LegacyEntity` that feed `ctx.dataLoader.*.load(...)` may not typecheck under structural narrowing. Prefer narrowing if it compiles; otherwise flag a boundary conversion helper (doc option 3) and instruct the agent to grep-verify no consumer reads a fabricated field. Run jenny's pre-flight checks before deciding.
6. **GraphQL decorators stay legacy.** `@Query(() => LegacyEntity)`, `@Resolver(LegacyEntity)`, `PaginatedResponse(LegacyEntity)` keep their legacy `@ObjectType()` classes; only TS return/`@Parent()` types become `Mapped*`. NestJS walks `@Field()` by name, so the mapped shape serializes identically.
7. **Asymmetric scalar transforms and renames.** Any column where the Prisma field name or type differs from the legacy entity (e.g. `displayViewSelectRequirement` vs `displayViewRequirement`) must be named explicitly in the mapper snippet in the card.
8. **Null coercion (PAY-3476/3533).** Nullable legacy field feeding a non-nullable Prisma column, or vice versa: name the coercion (e.g. `null` to `[]`) explicitly; never let the mapper decide silently.
9. **App-side vs DB-side defaults (PAY-3890, SEV-4).** If TypeORM set a default in the entity and Prisma relies on the DB (or neither does), the card must state which side owns the default post-swap.
10. **Explicit `null` in a find-options `where` was INERT on TypeORM; Prisma enforces `IS NULL`.** (Phase-2 divergence #5, new in 0.3: `invalidWhereValuesBehavior` defaults to `'ignore'`, so a bare `null` value is dropped just like `undefined`; only `IsNull()` reliably means SQL `IS NULL` under the live config. Derived from `typeorm@0.3.30`: `SelectQueryBuilder.js:2505-2517`.) Porting a bare-`null` filter verbatim to Prisma `null` ENFORCES a filter that was previously a no-op, a product behaviour change, not a mechanical port. Check the legacy call site: `IsNull()` ports straight to Prisma `null` (already matching); a bare `null` needs the intended behaviour decided explicitly and recorded in the card's Q&A. Preventive: zero bare-null find-options sites exist in `src/` today; the two `IS NULL` sites use `IsNull()` correctly.
11. **`update()` SET-payload `undefined` now SKIPS the column; an all-`undefined` payload THROWS.** (Phase-2 divergence #6, flipped at the bump: 0.2.30 bound undefined as SQL NULL and CLEARED the column; 0.3.30 filters undefined keys out of the SET list, `UpdateQueryBuilder.js:294-300`, then throws `UpdateValuesMissingError` if nothing survives, `:431-432`. Prisma also skips undefined keys but NO-OPS on an all-undefined data payload instead of throwing.) For any write spreading optional keys: check whether the service explicitly restored the 0.2 clear-on-undefined contract with a `?? null` coalesce (the `OrderingWindowService.updateMany` pattern, CUSM-1017 / #4217); if so, the Prisma port must reproduce the RESTORED contract, coercing `undefined` to `null` for those fields. If no restore exists, the current legacy behaviour is already 'skip'; a verbatim port matches it, but flag it if the un-cleared column looks like a live bug the bump introduced (the 'dead behaviour' case). A single-optional-field update swaps a TypeORM throw for a Prisma silent no-op; the card decides which behaviour ships and says so. The tri-state relation rule inherits the caveat: 'undefined leaves the FK alone' only holds while some other field is being written.

## Write-path decision (the incident rule)

Classify every in-scope method as read or write, then:

- **Read-only card**: state in Out of scope, verbatim style: 'Write-path audits (FK carve-outs, transform inverses, tri-state, null coercion, default parity, column completeness). All N methods are reads; the doc's write-path machinery does not apply. State this in the PR.' Repeat it as a Verification checkbox. Name the sibling tickets where the store's mutation methods swap, so the agent leaves their TypeORM internals and `@InjectRepository` params alone.
- **Card touching writes**: no bridging mappers. Write methods take `Prisma.<Entity>UncheckedCreateInput`/`UncheckedUpdateInput` directly; `Partial<EntityRecord>`, entity instances, and legacy-shaped DTOs are banned parameter shapes. Mandate a round-trip write test (the CUSM-770 class: write, re-read, assert every column survived, especially FKs and transformed scalars). Cite CUSM-770/795/796 in the card so the agent understands the stakes. Additionally run footgun 11 on every update that spreads optional keys: name any clear-on-undefined restore (`?? null` coalesce) the Prisma port must reproduce, and decide the all-undefined-payload behaviour (TypeORM throw vs Prisma no-op) explicitly. Pin what the live service does today, not what a rule's name says.

## Extended card template (delta over linear-write)

Use the base template, plus these sections in this order (see the exemplar for a complete instance):

- `## Governing docs (read before coding)` after Summary: the Step 0 doc list with one-line ownership notes.
- `## Implementation guidance` structured as: footgun blocks first (bold, numbered, with evidence), then lettered phases matching the Phase 2 doc checklist (A decouple types, B build mapper, C swap each query with a per-method fenced snippet using `// 👇`/`// 👈` markers on the trap lines, D update consumers narrow/widen/convert), then `### Constructor wiring`, then `### When uncertain` ending with 'fix the query, not the snapshot' and 'stop and surface rather than reaching for `Object.assign`, `as`, or `$queryRawUnsafe`'.
- `## Testing`: service-level integration spec path, the read matrix to cover (matching rows, exclusion, ordering, pagination, empty search, cross-venue isolation, soft-delete exclusion, nullable-boolean case), snapshot rules, no-mocking rule.
- `## Stacked PR shape`: PR 1 lands the service-level specs green against the current TypeORM code; PR 2 stacks on it with commit 1 (type-only `Mapped*` decoupling) and commit 2 (mapper + swap + consumer narrowing), every PR 1 assertion and Phase 1 snapshot unchanged. If research (workflow step 3) found a pre-bump Phase 1 baseline that fails an unmodified re-run, a re-pin commit precedes everything, isolated and evidenced per the non-negotiable above. Review pass before pushing: run the dedicated `typeorm-prisma-migration-reviewer` agent (its ranked dimensions are the merge bar); then CodeRabbit.
- `## Verification`: the repo validation chain in order (`npm run fix:formatting && npm run fix:linting`, then `check:typing`/`check:linting`/`check:formatting`, then `npm run test:unit -- <domain>`, then `npm run test:integration -- <domain>`), plus `git grep` checkboxes proving no `createQueryBuilder`/`getManyAndCount` in swapped methods, no legacy-entities import in the mapper, no `as`/`Object.assign` in the diff, and the write-path N/A note where applicable.
- `## Q&A`: every corrected guess from the original card as a Q/A pair; every question answered during the rewrite.
- `+++ # Original description (pre-YYYY-MM-DD)` collapsible, verbatim, at the bottom.

Risk tiering: an internal read-query swap behind stable signatures, Phase 1 snapshots, and new service specs, with no schema, write-path, or GraphQL contract change, is Low. Anything touching writes starts at Medium and cites the incident lineage.

## Save mechanics reminders (inherited, most-burned subset)

- `+++ Title` / `+++` for collapsibles, never `<details>`.
- Bullets, not numbered lists; blank lines between bullets near fenced blocks; fetch back after save and verify nothing was clipped.
- Backtick `@mr-yum/*` package names so Linear does not parse `@` as a mention.
- Symbol citations as `` `Class.method` `` followed by a hyperlinked `([GitHub](...#L123))` label, or `file.ts:line` when linking is impractical.
- No em dashes anywhere in the card.
